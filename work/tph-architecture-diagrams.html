Temenos Payment Hub · Architecture

The TPH engine, and how an ACH clearing attaches to it

Two drawings. The first shows why TPH behaves the way it does — a pipeline of independent components whose logic lives in parameter tables rather than in code. The second shows the asymmetry that makes ACH clearing work: outward is a bulking problem, inward is a debulking problem.

1 · The TPH engine

The mechanism worth seeing is not the list of components — it is that no component contains its own business logic. Each resolves behaviour at runtime from the parameter plane beneath it, and a single table decides which physical program a component runs, or whether it runs at all.

Why this shape matters

Estimating a TPH change means asking which plane it lands in. A behaviour change is usually a parameter record. A new component is almost never possible. A new rule that no table expresses is the extension layer.

What the diagram omits

Queues and warehousing are shown only as the sideways exits. The full 57-step ordering lives in the STP flow breakdown — this drawing is about structure, not sequence.

Verified against

Component names are the delivered PP.*Service list from the R25 Payments release highlights. Table names come from the extracted JAR schemas and Intro Temenos Payments.

2 · ACH clearing attached to TPH

Scope boundary

This is the generic TPH domestic ACH clearing architecture, drawn from the delivered clearing framework and the inward mapping framework. It is not CBOJ-specific — the CBOJ IRD has not been supplied. Message types shown are the standard ISO 20022 ACH set; the actual CBOJ message list, versions, purpose codes and return reason codes must come from the IRD. Whether CBOJ ACH is a delivered adapter or a Local Clearing Extension build is unknown and unestimated.

The two directions are not mirror images. Outward accumulates many payments into one file on a clock; inward takes one file and explodes it into many payments. Different tables control each, and the settlement booking sits between them.

The escape hatch

FileGenerationRequired = N tells TPH not to build the file at all. Payments park at status 990 and an implementation layer produces the file, then updates status by OFS or the Provider API. This is the fork that decides most of the build effort.

The reconciliation trap

If DD and CT bulk into one file, both PP.CLEARING.SETTING records need the same Settlement Booking Indicator. Mismatched, you get files whose nostro bookings do not reconcile — and it surfaces late.

What is still unknown

Everything CBOJ-specific: message versions, purpose codes, return reason codes, STP rules, the ACH/RTGS split, and whether file generation is even done by TPH. All of it needs the IRD.
