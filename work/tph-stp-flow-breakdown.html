TPH STP Process Flow — step-by-step breakdown

Every box on the STP flow diagram, in processing order, with the one thing an implementation team actually needs to know about each: does the engine already do this, do you configure it, or do you have to build it?

Source docs/TPH STP Flow New.jpg Steps 57 Stages 6 Grounding R25 Payments service list · PP.* parameter tables · Payments Extensibility

How each step is classified

Three categories, applied as a primary answer per step. Most TPH steps are a delivered service whose behaviour comes entirely from parameter tables — where that setup is the real work, the step is marked Configuration even though the code is core. A dashed secondary chip flags the other dimension.

Core

29of 57 steps

The engine performs this itself. A delivered PP.*Service runs it; there is nothing to set up beyond switching the component on, and nothing to write.

Owner: none — it just runs

Configuration

25of 57 steps

Core code, client-specific behaviour. The outcome is driven by records in PP.* parameter tables resolved by peel-off logic. No code, but real analysis and setup effort.

Owner: business / implementation consultant

Customisation

3primary · 12 conditional

Something must be built: a Python extension, a scheme adapter, an interface to a third-party or non-Transact system. 12 further steps turn custom only under a stated condition.

Owner: development team

Intake & message acceptance

Steps 1–13
01

Delivering channels

Payments arrive from nine channel types shown across the top band: Payment Order, Local Clearing, Delivery (SWIFT MX), SAA (SWIFT MT), Host Systems, Other Banks, Direct Debit Initiation (DD/DDI), Debit Collection and Teller (cheques). Retail/Corporate/Wealth channels and Transact AA & STO feed in through Payment Order.

  • ConfigPP.SOURCEPP.MSG.FORMAT.PER.CHANNELPP.MSGPAYMENTTYPECHANNEL

Turns custom when: a proprietary host system or in-house channel needs its own adapter into the messaging framework.

Configuration+ custom adapter
02

Message Acceptance & Enrichment

The single entry point for every channel. Accepts the inbound message, applies file- and bulk-level duplicate checks and enriches it before anything else runs. MT19x / MT29x investigation messages are diverted straight to the Transact Delivery Module rather than into the payment flow.

  • ServicePP.MessageAcceptanceService
  • ConfigPP.MSG.ACCEPTANCE.PARAMPP.MSGMAPPINGPARAMETER
Core+ param setup
03

Bulk detection & Batch Server debulking

A decision tests whether the message is single-debit/multiple-credit (CT) or single-credit/multiple-debit (DD). If yes, the Batch Server debulks the file into a parent and its children; if no, the message continues as a single payment.

  • ServicePP.BatchServerServicePP.LocalClearingDebulkingService
Core
04

Parent / children release control

The Batch Server holds the release-of-parent and release-of-children gates. A test on whether the parent is rejected or finalised decides the children's fate — if the parent is not viable, the children are cancelled.

  • OutcomeCancel Children
Core
05

Submitter validation

Confirms the sending party is a known, authorised submitter for the channel and source the message arrived on. First of the eight checks in the validation block.

  • ConfigPP.SOURCE (channel · source product · source product group)
Configuration
06

Mapping

Maps the inbound format (MT, MX, clearing file, order) onto the TPH neutral payment structure. Mapping parameters decide, for example, whether an inbound pacs.008 from STEP2 follows the credit transfer flow.

  • ServicePP.MessageMappingServicePP.LocalClearingMsgMapService
  • ConfigPP.MSGMAPPINGPARAMETER

Turns custom when: the format is not a delivered one — a bespoke host layout or a domestic scheme file needs mapping built in the messaging framework.

Configuration+ custom formats
07

Capture message

Persists the raw inbound message so it can be replayed, audited and shown in the GUI regardless of what the rest of the flow does with it.

Core
08

Technical duplicate check

Detects re-sent messages at file, bulk and message level before any business processing. Distinct from the business duplicate check later in the flow (step 38).

  • ConfigPP.MSG.ACCEPTANCE.PARAM Check Duplicate Indicator · EB.DUPLICATE.TYPE
Configuration
09

Validation of basic structure

Syntactic validation of the message against its format definition — mandatory fields, field lengths, code validity. Failures drop out as invalid transactions.

Core
10

Assign TRN & TRN enrichment

Generates the Transaction Reference Number that identifies the payment for its whole life, then enriches the payment record around it.

  • ServicePP.TransactionReferenceGenerationService
Core
11

Transform message

Converts the validated message into the internal payment object the processing block consumes, applying any format-specific transformation rules.

Turns custom when: client-specific enrichment or attribute substitution is needed — this is the natural place for a Python extension writing to PP.POR.EXTENSION.

Configuration+ extension
12

Invalid transaction → Exception Q

Anything failing the validation block is written to the Exception queue as an invalid transaction rather than being silently dropped. Picked up from the GUI for manual handling.

  • ArtefactInternal MQ — Exception Q
Core+ queue setup
13

Transact Delivery Module handoff

Investigation and answer messages (MT19x / MT29x) bypass STP entirely and are handed to the Transact Delivery Module from Message Acceptance.

Core

Classification, SLA & automated repair

Steps 14–17
14

Assign weight (L / M / H)

Every payment gets a high-level weight — light, medium or heavy — plus a specific weight. Weight is the single most powerful configuration lever in TPH: it decides which physical program each downstream component invokes, and whether a component is skipped altogether.

  • ServicePP.WeightAssignmentService
  • ConfigPP.SPECIFIC.WEIGHTPP.PROGRAMS.PER.WEIGHT
Configuration
15

Code words

Resolves inbound code words carried in the message into processing instructions, and prepares outbound code words for generation. Backed by the internal PAY component and its database.

  • ServicePP.InboundCodeWordServicePP.OutboundCodeWordService
Configuration
16

SLA determination

Assigns the processing service level — typically driven per code word — which governs cut-off behaviour and prioritisation for the rest of the flow.

  • ServicePP.SLADeterminationService
Configuration
17

Automated Repair Tool

Attempts rule-based auto-repair of incomplete or non-conforming payments before they reach the processing block, so they stay straight-through. Can call out to the external Temenos Repair service.

  • ServicePP.OrderEntryRepairService
  • ExternalExternal Repair Tool (Temenos Repair)

Turns custom when: the external repair tool is a third-party product rather than the Temenos one — the interface must be built.

Configuration+ external tool

Payment processing block — parties, product, accounts

Steps 18–40
18

Payment Initiation — assign static data

Opens the main processing block. Attaches all static data the payment needs — company, currency, country, BIC and clearing directory references — so downstream components resolve against consistent values.

  • ServicePP.PaymentInitialisationService
  • ConfigStatic Data · PP.COUNTRY.IBAN.STRUCTURE
Core+ static data
19

Liquidity management

Applies liquidity rules and priority to the payment before parties are resolved, so funding constraints are known ahead of the balance checks.

Configuration
20

Debit party determination

Identifies who is being debited and derives the debit bank account. Reads bank conditions to resolve debit bank account and debit bank condition attributes.

  • ServicePP.DebitPartyDeterminationServicePP.BankConditionsService
  • ComponentBank Conditions (internal, PAY)
Core+ bank conditions
21

Warehouse decision

A gate immediately after debit party: if the payment is to be warehoused it loops out of the main path here and is parked until its due date, otherwise processing continues.

  • ServicePP.WarehouseService
Core
22

Own account determination

Establishes whether debit and credit sides belong to the same client — an own-account transfer — which changes charging, posting and routing downstream.

  • ServicePP.OwnAccountDeterminationService
Core
23

Direction determination

Classifies the payment as outgoing, incoming, book or redirected. This is the value the two direction branches later in the flow switch on.

  • ServicePP.DirectionDeterminationService
Core
24

Debit authority

Confirms the bank is authorised to debit the account. Checks direct debit mandates and transaction stops held in Transact, and skips the check entirely for message types listed as no-debit-authority.

  • ServicePP.DebitAuthorityService
  • ConfigPP.NODA.LIST
  • ExternalDD Mandate (Transact/External) · Transaction Stop (Transact)
Configuration
25

Product determination

Derives the payment product from the weight-specific product condition tables. The product then links the payment to its fee, ledger, client condition, posting and routing products — so this record set drives most downstream behaviour.

  • ServicePP.ProductDeterminationService
  • ConfigPP.HEAVYWEIGHTPRODUCTCONDPP.MEDIUMWEIGHTPRODUCTCONDPP.LIGHTWEIGHTPRODUCTCOND
Configuration
26

Direction branch — debit side

The flow forks three ways on direction: Outgoing Debits (DD / RF / RD), Outgoing & Redirect Credits (RT / CT), and Incoming / Book. Each branch takes a different path to account validation.

Core
27

Routing & settlement (debit side)

For outgoing debits, selects the settlement channel and correspondent path. Resolution is by contract specificity: party contract, then country contract, then bank contract.

  • ServicePP.RoutingAndSettlementServicePP.RoutingAndSettlementDASService
  • ConfigPP.CONTRACTPP.RSCHANNEL.SELECTION
Configuration
28

Credit side determination

For incoming and book payments, resolves the credit side of the payment before the accounts are validated.

  • ServicePP.CreditPartyDeterminationService
Core
29

Validate main accounts

Both branches converge here. Validates the debit and credit main accounts against Account and Customer Info — existence, status, currency, blocks.

  • ExternalAccount and Customer Info (Transact / External)

Turns custom when: accounts live in a non-Transact core — the Account and Customer Info interface has to be built against the external system.

Core+ external core
30

Balance check (without charges)

First funds check, on the principal amount only, via a balance request to Transact. A conditional path handles the case where the parent account has insufficient balance in a bulk.

  • ServicePP.BalanceCheckServicePP.BalanceInterfaceService
  • ConfigPP.BALANCE.CHECK.REQUIRED
Core+ required flag
31

Interpret debit party client conditions

Applies the client's agreed conditions on the debit side — special handling, charging options, processing preferences — resolved by peel-off from generic to client-specific records.

  • ServicePP_ClientConditionsService
  • ConfigPP.CLIENT.CONDITIONRECORDPP.CLIENTCOND.PRODUCT
Configuration
32

Validate credit party

Second direction branch. Outgoing redirect credits go via routing & settlement first; incoming, book and outgoing redirected debits validate the credit party directly against the reference/clearing directory.

  • ExternalReference Directory (Transact)
Core+ directory load
33

Beneficiary Name Check (BNC)

For incoming and book customer CT/DD payments, matches the beneficiary name on the message against the account holder's name using the Temenos Name Matching Service.

  • ExternalTemenos Name Matching Service (Transact only)

Turns custom when: a third-party name-matching engine is used instead of the Temenos service.

Configuration+ 3rd-party matcher
34

Credit client / bank condition

The credit-side mirror of step 31 — client conditions and bank conditions applied to the beneficiary side, each with their own conditions-processing path.

  • ExternalAccount & Customer Info (Transact / External)
Configuration
35

Charge accounts validation

Validates the debit and credit charge accounts that fees will later be posted to, before fee determination commits to them.

  • ConfigPP.FEETYPECREDITACCOUNT

36

Date determination

Derives processing date, debit value date and credit value date using holiday logic and send-date parameters, both resolved by peel-off.

  • ServicePP.DateDeterminationService
  • ConfigPP.HOLIDAY.LOGICPP.SEND.DATE
Configuration
37

Cover determination

Decides whether a cover payment is required and matches incoming covers against their underlying payments via the Cover Matching component in Transact.

  • ServicePP.CoverDeterminationService
  • ExternalCover Matching (Transact)

38

Duplicate check (business)

Business-level duplicate detection on the fully enriched payment — same debtor, amount, beneficiary and date — as opposed to the technical duplicate check at step 8.

  • ServicePP.DuplicateCheckService

39

Payment finalisation — release children

Closes the processing block. Finalises the payment and releases child payments of a bulk. Anything flagged for repair leaves the STP path here into the manual Repair Q.

  • ServicePP.PaymentFinalisationService
  • ExceptionRepair Q (manual)
Core
40

Account cash position update

Updates the cash position for the accounts involved and pushes it to Position Management, so intraday liquidity reflects the payment before it is booked.

  • ExternalPosition Management — PM (Transact / External)

Turns custom when: position management sits in an external treasury system.

D

Compliance, value calculation & booking

Steps 41–48
41

Sanction screening

Inspects the payment against the sanctions filter and applies the result: seize funds, return/reject for incoming, cancel for outgoing, or continue processing. Runs as daily filtering as well as inline, and feeds the repair path on a hit.

  • ServicePP.TemenosAMLServicePP.NorkomAMLService
  • ExternalSanction Screening (Transact / External)

Why custom: TPH orchestrates the decision and the outcome handling, but the filter itself is an external engine. Unless you use a delivered adapter, the request/response integration, hit handling and rescreen behaviour are a build item on every project.

Customisationcore orchestration
42

Future due date → warehousing

Tests whether the payment is due in the future. If yes it goes to Payment Warehousing (or Output Warehousing) and re-enters the flow on the due date; if no it continues immediately.

  • ServicePP.FutureDueDateServicePP.WarehouseService
Core
43

Risk filtering

Applies risk conditions defined per correspondent bank, country and currency. A hit routes the payment to the RFQ queue where it is either stopped or released to continue.

  • ServicePP.RiskFilterService
  • ConfigPP.RISK.FILTER.CONDITIONS
Configuration
44

Fee determination

Calculates charges and tax from the client charges table against the fee product derived at product determination. For bulks, the parent is released only after all child fees are determined.

  • ServicePP.FeeDeterminationServicePP.FeeTypesService
  • ConfigPP.CLIENTCHARGESPP.FEE.PRODUCT
  • ExternalCharges / Tax (Transact)
Configuration
45

FX conversion

Converts the amount where debit and credit currencies differ, retrieving the exchange rate from the Rate Interface in Transact and selecting the open currency position account for the posting.

  • ExternalRate Interface (Transact)
  • ConfigPP.OCP.ACCOUNTPP.CURRENCY.DEALER

46

Balance check (including charges and FX)

Final funds check on the true total. Conditional paths cover cut-off time breaches, booking errors, and insufficient balance on a bulk parent account.

  • ExternalBalance Request (Transact / External / FAMS)

Turns custom when: funds authorisation runs through FAMS or an external balance provider rather than Transact directly.

Core+ FAMS / external
47

Posting scheme & booking

Selects the posting set from company, posting product and payment attributes, then books the entries to the Transact or external ledger. Drives statement output (MT940/950, camt.053/054) and reconciliation.

  • ConfigPP.POSTING.SETPP.LEDGER.PRODUCT.CODESPP.STATEMENT.FORMAT
  • ExternalTransact / External Ledger → Reconciliation

Turns custom when: booking goes to a non-Transact general ledger — the ledger interface and reconciliation feed must be built.

Configuration+ external ledger
48

Claim processing

Raises charge claims that result in MT191 or MT199. A claim is logged for inbound or redirected payments when field 71G is insufficient and there is no account to debit, or for a periodical charging request.

  • ServicePP.ClaimsService

Output generation & delivery

Steps 49–54
49

Future send date → output warehousing

Final gate before the Output block. A payment already booked but not yet due for despatch is held in Output Warehousing until its send date.

50

Payment generation — SWIFT

Generates the outbound SWIFT message in the required flavour (MT, MX, TARGET2 MX, CHAPS MX) and hands it to SAA / Delivery, which passes it through the external filter service before despatch.

  • ServicePP.PaymentGenerationServicePP.SwiftOutServicePP.TARGET2Service
  • ExternalSAA (SWIFT) / Delivery → External Filter Service (Fircosoft)

Turns custom when: the outbound filter is a third-party product such as Fircosoft — the interface and its response handling are built, not configured.

Configuration+ filter interface
51

Payment generation — clearing

Generates the clearing file or message for the domestic scheme, writes it to the Clearing Out Q and despatches it externally. Bulking criteria and settlement booking indicator must stay in sync per transaction type.

  • ServicePP.ClearingFrameworkServicePP.LocalClearingBACSServicePP.STEP2Service
  • ConfigPP.CLEARING.SETTINGPP.CLEARING.RETURNCODEPP.CLEARING.NATURE.CODE

Why custom: configuration only covers schemes Temenos already delivers (SEPA, BACS, TARGET2, STEP2, CHAPS, HKCLG). Any other domestic scheme needs a Local Clearing Extension built — mapping, bulking, return handling — and this is typically the largest single development workstream on a TPH implementation.

Customisationconfig if delivered scheme

Confirmations & advices

Produces debit/credit XML advice, print advice, phone advice and SMS/email, gated on the credit advice indicator in client conditions. Output goes to Auto Form and Output Management for despatch.

  • ServicePP.ConfirmationsServicePP.EmailSMSServicePP.PrintService

Turns custom when: bank-branded advice templates or a non-standard notification channel are required.

55

COB extracts

End-of-day batch extracts off the completed payment set: AML batch extract, billing batch extract, Insight batch extract and archive, delivered onward through Transact Delivery.

  • ServicePP.SODEODServicePP.BillingServicePP.InsightService

Turns custom when: the AML extract must match a specific vendor's file specification.

Configuration+ vendor format
56

GUI — order entry, enquiries, repair, static data

The operational front end: manual order entry, payment enquiries, the repair workbench, and maintenance of static data for client conditions, code words, fees, product determination, posting scheme and routing & settlement.

  • ServicePP.GUIFrameworkService
  • ConfigUser roles · PP.AUTHORIZATIONPRINCIPLE (4-eye / 6-eye)
Core+ roles
57

Client extensions — the sanctioned customisation point

Not a box on the diagram, but the mechanism that hangs off it. Python extensions in the messaging framework (Camel layer) enrich payment attributes, override values and raise custom validations. The extension writes a JSON payload to the PP.POR.EXTENSION landing table, which TPH substitutes into the payment while processing. Errors are raised at a named stage: Debit Party, Credit Party or Date Validation.

  • LandingPP.POR.EXTENSION
  • ContextGET APIs — payment dates · porsupplementaryinfo

Why custom: this is where client-specific business rules belong. Using the extension framework instead of modifying core keeps the implementation upgrade-safe.

Reading the classification correctly

Four things that decide the answer for any step

  • Weight is the master switch. PP.PROGRAMS.PER.WEIGHT specifies which physical program each component invokes per weight and specific weight — and whether the component is skipped entirely. A step marked Core can still be turned off here without code.
  • Peel-off logic means configuration is layered, not flat. Client conditions, bank conditions, product conditions and holiday logic all resolve from the most specific matching record down to the most generic. Estimate by the number of condition layers, not the number of tables.
  • "External" on the diagram does not automatically mean custom. Boxes annotated Transact are a delivered interface — configuration. Boxes annotated Transact / External are only a build when the external option is taken.
  • Customisation belongs in the extension framework. Client-specific behaviour goes through Python extensions and PP.POR.EXTENSION, not modified core code — that is what keeps the implementation upgrade-safe across releases.
