# TPH Customisation Routines — Verified Patterns from Production Code

Two real, compiled TPH customisation routines were read in full. They are the
only end-to-end examples of TPH customisation in the artifacts, and they settle
several questions the working brief flagged as unconfirmed (§0.35, *"custom-hook
interface signatures are unconfirmed … do not invent one"*).

Source: `D:\Learning\TPH-Routines\` `[CLIENT]`

**Scope warning.** `SARIE` is the Saudi Arabian Riyal Interbank Express RTGS, and
the `BAB_` / `BAB.` prefix is that bank's own module prefix. These are *not* SEPA
routines. What transfers to a SEPA implementation is the **hook signature, the
`$USING` set, the equate namespaces and the wiring mechanism** — not the business
logic, the clearing, or the routine names.

## Pattern 1 — a `PP.COMPONENT.API.HOOK` component API

`BAB.TPH.CREDIT.PARTY.CHECK.b`, compiler version **R23_SP12.0**, validated
2025-05-15. `[CLIENT]`

Its own header states the wiring:

> `*This routine is attached as CreditPartyDetermination hook in PP.COMPONENT.API.HOOK`

That matches the two-field `PP.COMPONENT.API.HOOK` record confirmed in the
schema: `PP.CAH.HookAPIName` = `CreditPartyDetermination`,
`PP.CAH.InvokeCall` = the routine name. `[SCHEMA]` `[CLIENT]`

### Confirmed signature

```basic
$PACKAGE BAB_TPHSwift

SUBROUTINE BAB.TPH.CREDIT.PARTY.CHECK(iTransactionContext, iAdditionalContext, oHookApiOutput)
```

Three arguments — two in, one out. This is the shape of a TPH component API hook
routine. `[CLIENT]`

### Confirmed `$USING` set

```basic
$USING EB.Updates
$USING PP.PaymentFrameworkService
$USING PP.CreditPartyDeterminationService
$USING PP.PaymentWorkflowDASService
$USING EB.API
$USING PP.PaymentWorkflowGUI
$USING EB.SystemTables
$USING PP.OrderEntryGUI
$INSERT I_F.ACCOUNT
```

Every one of those maps to a JAR in this set: `PP_PaymentFrameworkService.jar`,
`PP_CreditPartyDeterminationService.jar`, `PP_PaymentWorkflowDASService.jar`,
`PP_PaymentWorkflowGUI.jar`, `PP_OrderEntryGUI.jar`. `[JAR]`

### Confirmed equate namespaces

| Purpose | Equate |
|---|---|
| Credit account (input) | `PP.CreditPartyDeterminationService.DetermineCreditPartyInput.crMainAccNumber` |
| Transaction amount (input) | `PP.CreditPartyDeterminationService.DetermineCreditPartyInput.transactionAmount` |
| Incoming message type (input) | `PP.CreditPartyDeterminationService.DetermineCreditPartyInput.incomingMessageType` |
| POR id | `iTransactionContext<2>` |
| `POR.SUPPLEMENTARY.INFO` party role | `PP.PaymentWorkflowGUI.PorSupplementaryInfo.PorIdPartyRole` |
| `POR.SUPPLEMENTARY.INFO` party name | `PP.PaymentWorkflowGUI.PorSupplementaryInfo.PorIdName` |
| Response type (output) | `PP.PaymentFrameworkService.HookApiResponse.responseType` |
| Response text (output) | `PP.PaymentFrameworkService.HookApiResponse.responseText` |

`[CLIENT]`

### Confirmed conventions

- **The beneficiary is found by party role, not position.** The routine does
  `LOCATE 'BENFCY' IN R.POR.SUP<...PorIdPartyRole,1> SETTING TYPE.POS` and then
  reads `...PorIdName,TYPE.POS`. `PorIdPartyRole` and `PorIdName` are parallel
  multivalue fields. Never index them by a hard-coded position.
- **The credit account arrives as `<AccountId>*<IBAN>`.** The routine splits with
  `FIELD(CREDIT.ACC,"*",1)` / `FIELD(CREDIT.ACC,"*",2)` and then strips leading
  zeros from the account id with `TRIM(CR.AC, "0", "L")` before `F.READ` on
  `F.ACCOUNT`.
- **Rejecting a payment** = set `responseType = 'ERR'` and put the operator-facing
  reason in `responseText`. That is what moves the payment to the repair queue.
- Structure is standard T24: `GOSUB OPEN.FILES` / `INIT.VARIABLES` / `<work>` with
  `CALL OPF` per file in `OPEN.FILES`.

### Skeleton for a SEPA equivalent

```basic
* @ValidationCode : <generated by the compiler — do not hand-write>
$PACKAGE <YourModule>_<Area>
*-----------------------------------------------------------------------------
* <Rating>70</Rating>
*
* Attached as <HookAPIName> hook in PP.COMPONENT.API.HOOK
* Purpose: <one line>
*-----------------------------------------------------------------------------
    SUBROUTINE <YOUR.ROUTINE.NAME>(iTransactionContext, iAdditionalContext, oHookApiOutput)

    $USING PP.PaymentFrameworkService
    $USING PP.CreditPartyDeterminationService
    $USING PP.PaymentWorkflowGUI
    $USING EB.SystemTables

    GOSUB OPEN.FILES
    GOSUB INIT.VARIABLES
    GOSUB VALIDATE

RETURN
*-----------------------------------------------------------------------------
OPEN.FILES:
*-----------------------------------------------------------------------------
    FN.POR.SUP = "F.POR.SUPPLEMENTARY.INFO" ; F.POR.SUP = ""
    CALL OPF(FN.POR.SUP, F.POR.SUP)
RETURN
*-----------------------------------------------------------------------------
INIT.VARIABLES:
*-----------------------------------------------------------------------------
    PorId = iTransactionContext<2>
    CALL F.READ(FN.POR.SUP, PorId, R.POR.SUP, F.POR.SUP, POR.SUP.ERR)
RETURN
*-----------------------------------------------------------------------------
VALIDATE:
*-----------------------------------------------------------------------------
    IF <your condition fails> THEN
        oHookApiOutput<PP.PaymentFrameworkService.HookApiResponse.responseType> = 'ERR'
        oHookApiOutput<PP.PaymentFrameworkService.HookApiResponse.responseText> = '<reason>'
    END
RETURN

END
```

Before using any `POR.*` field in such a routine, verify it:

```
python pipeline/validate_fields.py --app POR.SUPPLEMENTARY.INFO --fields "<F1>,<F2>"
```

## Pattern 2 — a `PP.STATUS.ACTION` status-code routine

`BAB.SARIE.SW.CLRNG.MSG 2.b`, developer *Naga, Jayanth — ORION*, 7 May 2025.
Header: *"This Routine triggered for PP.STATUS.ACTION Status Code. Reads Payment
Record and POST FUNDS TRANSFER OFS."* `[CLIENT]`

### Confirmed signature

```basic
$PACKAGE TPH.UTL.OUTSWIFT

SUBROUTINE BAB.SARIE.SW.CLRNG.MSG(iStatusActionLoc)
```

One argument — a status-action context array. `[CLIENT]`

### Confirmed context layout

```basic
yPaymentRecord           = RAISE(iStatusActionLoc<8>)
yAdditionalPaymentRecord = RAISE(iStatusActionLoc<9>)
```

Positions 8 and 9 carry the payment record and additional payment record, each
delimited one level down — hence `RAISE`. `[CLIENT]`

### Confirmed `PaymentRecord` equates

`PP.PaymentWorkflowDASService.PaymentRecord.` + `companyID`, `ftNumber`,
`clearingTransactionType`, `originatingChannel`, `statusCode`, `debitClientID`,
`debitMainAccount`, `debitMainAccountCurrencyCode`, `debitMainAmount`,
`creditMainAccount`, `creditMainAccountCurrencyCode`. `[CLIENT]`

Required inserts:

```basic
$INSERT I_PaymentWorkflowDASService_PaymentID
$INSERT I_PaymentWorkflowDASService_PaymentRecord
$INSERT I_PaymentWorkflowDASService_AdditionalPaymentRecord
```

### Confirmed OFS pattern from a TPH routine

```basic
EB.Foundation.OfsBuildRecord(yAppName, yOfsFunc, yProcess, yOfsVers, yGtsMode, _
                             yNoOfAuth, yrecId, rRecFT, yOfsRecord)
EB.Interface.OfsCallBulkManager(yOfsSourceId, yOfsRecord, yOfsResponse, yTxnCommitted)
```

with `yAppName = 'FUNDS.TRANSFER'`, `yOfsFunc = 'I'`, `yProcess = 'PROCESS'`,
`yOfsVers = 'FUNDS.TRANSFER,OT102'`, `yGtsMode = '1'`, `yNoOfAuth = '0'`,
`yOfsSourceId = 'FUNDS.TRANSFER.OFS'`, and the record built with
`FT.Contract.FundsTransfer.<Field>` equates. `[CLIENT]`

### Defects in this sample — do not copy them

Read this routine as evidence of the *interface*, not as a model of quality:

1. **`DEBUG` is left in the shipped source** (line 23). That halts into the
   debugger at runtime. It must not reach an environment.
2. **`YNoofAuth` is assigned but `yNoOfAuth` is passed** (lines 86/94). jBC
   variable names are case-sensitive, so `OfsBuildRecord` receives an unassigned
   variable. The same typo appears in both OFS blocks.
3. **No OFS response check.** `yOfsResponse` and `yTxnCommitted` are captured and
   never examined — a failed `FUNDS.TRANSFER` posting passes silently.
4. **`FORMRECOFS1` and `FORMRECOFS2` are byte-identical** apart from the variable
   name; the only real difference is the version (`OT102` vs `OT102.USREGS`).
   Two identical FTs are posted for one payment.
5. **`Y.POR.CREDIT.CUS` is initialised and never used**, and `BenCustomer` is set
   from `debitClientID` — probably not intended.
